# X402 Protocol Contract

This document freezes the paid operation protocol contract implemented by the gateway in `services/gateway/src/http/routes/operations.ts` with related behavior from `services/gateway/src/x402/*` and MCP parity from `services/gateway/src/mcp/runtime.ts`.

## Lifecycle Diagram (Text Sequence)

### HTTP paid call (x402 mode)

1. Client discovers operation metadata from `GET /api/v1/discovery/operations`.
2. Client sends operation call (`GET` or `POST`) with `idempotency-key`.
3. Gateway resolves operation by method + path.
4. Gateway computes fingerprint over `{ method, path, query, body }` + `operation.id`.
5. Gateway checks idempotency store.
6. If no `payment-signature`, gateway returns `402 PAYMENT_REQUIRED` with `payment-required` header.
7. If `payment-signature` exists, gateway decodes and verifies payment requirements.
8. Gateway verifies and settles payment through x402 server.
9. On settlement success, gateway executes operation.
10. Gateway returns `200` with canonical success body, canonical receipt, and `payment-response` header.
11. Gateway stores result for deterministic idempotent replay.

### HTTP paid call (MPP mode)

1. Client sends paid operation call with `idempotency-key`.
2. Gateway delegates payment handling to MPP runtime.
3. If MPP challenge required, gateway returns `402 PAYMENT_REQUIRED` with MPP headers/body.
4. If paid, gateway executes operation and returns `200` with canonical success body.
5. Gateway includes MPP receipt headers when provided by runtime.

### MCP paid tool call (in-process runtime)

1. Caller invokes tool with `operationId`, input payload, `idempotencyKey`, optional `paymentProof`.
2. Runtime validates operation and idempotency.
3. For paid tools, runtime verifies proof using in-memory verifier.
4. Runtime executes operation and returns canonical result with receipt.
5. Runtime stores result for deterministic idempotent replay.

## Request and Response Contracts for Paid Operation Calls

### Operation request (HTTP)

- Method: operation-defined (`GET` or `POST`)
- Path: operation-defined (from registry/discovery)
- Required header: `idempotency-key: <string>`
- Required for paid retry: `payment-signature: <x402 encoded payment payload>`
- Body:
- `GET`: no body
- `POST`: optional JSON body, must be valid JSON if present

### Canonical success response (HTTP and MCP)

Status: `200`

```json
{
  "ok": true,
  "data": {"...": "operation output"},
  "receipt": {
    "receiptId": "sha256(operationId:idempotencyKey)",
    "operationId": "<operation-id>",
    "paid": true,
    "paymentProofId": "<settlement tx id or mpp receipt id when present>"
  }
}
```

### Canonical failure response

```json
{
  "ok": false,
  "error": {
    "code": "<deterministic error code>",
    "message": "<human-readable message>",
    "details": {"optional": "json"}
  }
}
```

Deterministic error codes:

- `INVALID_REQUEST`
- `OPERATION_NOT_FOUND`
- `MISSING_IDEMPOTENCY_KEY`
- `IDEMPOTENCY_CONFLICT`
- `PAYMENT_REQUIRED`
- `INVALID_PAYMENT_PROOF`
- `PAYMENT_PROOF_REPLAY`
- `INTERNAL_ERROR`

## Required Headers (Idempotency and Payment Proof)

### Required request headers

- `idempotency-key` (required for all operation invocations)
- `payment-signature` (required only for paid HTTP operation execution in x402 mode)

### Response headers used by protocol

- `payment-required`: x402 challenge header generated by `encodePaymentRequiredHeader(...)`.
- `payment-response`: settlement response header generated by `encodePaymentResponseHeader(...)` on successful paid execution in x402 mode.
- `x-idempotent-replay: true`: returned when gateway replays stored response for an already-completed/failed key+fingerprint.

Note: additional payment headers can appear in MPP mode and are passed through from runtime.

## 402 Challenge Schema (Canonical Fields and Deterministic Behavior)

In x402 HTTP mode, missing or invalid payment for a paid operation returns:

- Status: `402`
- Header: `payment-required`
- Body: canonical failure with `error.code = PAYMENT_REQUIRED` or `error.code = INVALID_PAYMENT_PROOF`

Challenge requirements are built from operation + config with deterministic inputs:

- `scheme`: `exact`
- `network`: configured CAIP-2 network derived from `STELLAR_NETWORK_PASSPHRASE`
- `payTo`: `GATEWAY_PAY_TO_ADDRESS`
- `price.asset`: USDC SAC for selected network
- `price.amount`: `String(operation.priceStroops)`
- `maxTimeoutSeconds`: `GATEWAY_CHALLENGE_TTL_SECONDS`

Canonical deterministic behavior:

- Same operation price/config produce equivalent requirement semantics.
- Missing signature always yields `PAYMENT_REQUIRED` and a fresh challenge response.
- Invalid signature yields `INVALID_PAYMENT_PROOF` plus challenge header.

## Payment Proof Verification Rules

### HTTP x402 verification path

1. Decode `payment-signature` header.
2. Build operation-specific requirements (`exact`, payee, amount, network, ttl).
3. Match client payment payload against requirements.
4. Verify payment payload cryptographically via x402 server.
5. Settle payment via x402 server.
6. Reject on any mismatch/failure with deterministic `402 INVALID_PAYMENT_PROOF`.

### MCP verifier rules (current in-process runtime)

For `paymentProof` object:

- `proof.operationId` must equal invoked operation id.
- `proof.resource` must equal expected operation path.
- Amount checks:
- use `mppSummary.deliveredAmountStroops` when present,
- else sum `paymentLegs[].amountStroops` when present,
- else use `amountStroops`.
- Minimum amount must be `>= operation.priceStroops`.
- Proof must include either:
- signature proof (`signature` + `nonce` + valid `timestamp` freshness), or
- tx proof (`txHash`) that passes facilitator and payment inspector checks.
- `proofId` is single-use within proof age window; replay is rejected (`PAYMENT_PROOF_REPLAY`, `409`).

## Anti-Replay and Idempotency Rules

### Idempotency key semantics

- Scope: global key namespace in in-memory store.
- Key is bound to fingerprint `sha256(operationId + stable({method,path,query,body}))` for HTTP.
- Key is bound to fingerprint `sha256(operationId + stable(input))` for MCP.

### Deterministic outcomes

- Same key + same fingerprint:
- if pending: `409 IDEMPOTENCY_CONFLICT`
- if completed/failed: replay stored body, add `x-idempotent-replay: true`
- Same key + different fingerprint: `409 IDEMPOTENCY_CONFLICT`

### Payment proof replay prevention

- `proofId` is tracked in verifier memory until expiry (`GATEWAY_MAX_PROOF_AGE_MS`).
- Reuse before expiry returns `409 PAYMENT_PROOF_REPLAY`.

### Important paid-flow behavior (current implementation)

For paid HTTP operations, a `402` response is persisted as failed idempotent state for that key+fingerprint. Retrying with the same `idempotency-key` replays the stored failure. Client must use a new idempotency key after obtaining a challenge/payment proof.

## Retry and Timeout Rules

- Client must always send `idempotency-key`.
- If network timeout occurs before response is observed:
- retry with same key only when request payload is identical and payment already supplied.
- For paid calls where first attempt returned `402`, use a new key for paid retry.
- Challenge timeout window is governed by `GATEWAY_CHALLENGE_TTL_SECONDS`.
- Payment proof freshness window is governed by `GATEWAY_MAX_PROOF_AGE_MS`.
- Transaction inspection max age is governed by `GATEWAY_MAX_TX_AGE_MS`.
- Idempotency record retention window is `GATEWAY_IDEMPOTENCY_TTL_MS`.

## Error Matrix (Status + Error Codes + Deterministic Client Handling)

| HTTP Status | Error Code | Deterministic Trigger | Client Handling |
| --- | --- | --- | --- |
| 400 | `MISSING_IDEMPOTENCY_KEY` | Missing `idempotency-key` header | Regenerate request with key and resend |
| 400 | `INVALID_REQUEST` | Invalid JSON/body/registration payload | Fix payload shape and resend with new key |
| 402 | `PAYMENT_REQUIRED` | Paid op called without valid payment proof | Obtain challenge, pay, retry with new key |
| 402 | `INVALID_PAYMENT_PROOF` | Signature decode/match/verify/settle failure | Recreate payment proof, retry with new key |
| 404 | `OPERATION_NOT_FOUND` | Route not registered | Refresh discovery and select valid operation |
| 409 | `IDEMPOTENCY_CONFLICT` | Key in progress or key reused with different payload | Use different key, or wait and replay safely |
| 409 | `PAYMENT_PROOF_REPLAY` | Proof id reused within acceptance window | Create fresh proof/payment and resend |
| 500 | `INTERNAL_ERROR` | Unhandled runtime failure | Exponential backoff, alert operator, keep evidence |

## Settlement and Reconciliation Checklist

For each paid invocation, record:

- Request metadata: operation id, method/path, idempotency key, timestamp.
- Challenge evidence: `402` status, `payment-required` header value hash, challenge body.
- Payment evidence: `payment-signature` request hash or MPP receipt headers.
- Settlement evidence: `payment-response` header (x402) or runtime receipt header (MPP).
- Invocation result: canonical success/failure body.
- Receipt fields: `receiptId`, `operationId`, `paid`, `paymentProofId`.
- On-chain linkage when available: tx hash and explorer URL.
- Replay checks: whether response had `x-idempotent-replay: true`.

## API/MCP Parity Rules

- Operation identity parity:
- HTTP uses route lookup by method+path.
- MCP uses `operationId` tool name.
- Both execute through same operation executor and return canonical success/failure envelope.
- Both enforce idempotency and return deterministic replay results.
- Paid parity:
- HTTP uses x402/MPP payment middleware and headers.
- MCP currently accepts explicit `paymentProof` object in-process.
- Receipt parity:
- both return `receiptId`, `operationId`, `paid`, optional `paymentProofId`.
- Discovery freshness and cache invalidation note:
- discovery endpoints include `discovery.updatedAt` and `discovery.openapiHash` metadata, and `GET /api/v1/discovery/openapi.json` exposes OpenAPI hash header(s) for client cache invalidation.

Current gap: external MCP transport endpoint is not exposed yet; parity applies to in-process runtime behavior.
